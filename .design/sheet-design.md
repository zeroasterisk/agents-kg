# Google Sheet KG Ingestion Template -- Design Document

## Overview

This document defines the schema, lifecycle, and integration design for a Google Sheet
that serves as a document submission interface for the agents-kg pipeline. The sheet
allows human contributors (starting with Alan) to submit documents -- URLs, file paths,
or text snippets -- for ingestion into the Temporal Knowledge Graph.

The sheet is one of potentially many input interfaces. It writes to a common ingestion
queue that the pipeline consumes.

---

## 1. Column Schema

| Column | Required | Type | Purpose | Accepted Values / Notes |
|--------|----------|------|---------|------------------------|
| `row_id` | Auto | String (UUID) | Unique identifier for this submission row. Generated by the pipeline on first poll, never edited by humans. Used to track the row across sheet edits and in pipeline.db. | UUID v4 (e.g., `a1b2c3d4-...`) |
| `uri` | Yes | String | The document to ingest. URL, local file path, or `inline:<hash>` for pasted text. | `https://...`, `/path/to/file.md`, `inline:...` |
| `title` | Optional | String | Human-friendly label for this document. If blank, the pipeline extracts a title during the parse stage. | Free text |
| `source_type` | Yes | Enum | Classifies the document's authority level. Drives the confidence score on extracted edges. | `authoritative` (confidence 1.0), `theoretical` (confidence 0.6), `speculative` (confidence 0.3) |
| `content_snippet` | Optional | String | For inline text submissions -- paste the full text here instead of providing a URI. If populated, `uri` should be set to `inline:` followed by a short label. | Free text (multi-line) |
| `submitter` | Yes | String | Who submitted this row. Email address or name. | e.g., `alan@example.com` |
| `source_interface` | Auto | Enum | Which input interface created this row. Set automatically; do not edit manually. | `google_sheet`, `cli`, `api`, `slack_bot` |
| `submitted_at` | Auto | ISO 8601 | Timestamp when the row was first detected by the pipeline poller. | `2026-05-12T14:30:00Z` |
| `status` | Yes | Enum | Current lifecycle state of this submission. See Section 2 for the full state machine. | `submitted`, `queued`, `fetching`, `parsing`, `extracting`, `reviewing`, `ingested`, `failed`, `skipped`, `duplicate`, `dead_letter` |
| `status_detail` | Auto | String | Human-readable detail about the current status. Updated by the pipeline. | e.g., `Failed at fetch: HTTP 404`, `Duplicate of row a1b2...` |
| `pipeline_source_id` | Auto | Integer | Foreign key to pipeline.db sources.id. Links this sheet row to the internal pipeline record. Populated after the row is queued. | Integer or blank |
| `entity_count` | Auto | Integer | Number of entities extracted from this document. Populated after the extract stage. | Integer or blank |
| `edge_count` | Auto | Integer | Number of edges extracted from this document. Populated after the extract stage. | Integer or blank |
| `last_updated` | Auto | ISO 8601 | Timestamp of the most recent status change. | `2026-05-12T15:02:00Z` |
| `notes` | Optional | String | Free-text field for humans. The pipeline never reads or modifies this column. | Free text |

### Column Ownership

Columns fall into three ownership categories:

- **Human-writable**: `uri`, `title`, `source_type`, `content_snippet`, `submitter`, `notes`, `status` (with constraints)
- **Pipeline-writable**: `row_id`, `source_interface`, `submitted_at`, `status`, `status_detail`, `pipeline_source_id`, `entity_count`, `edge_count`, `last_updated`
- **Shared**: `status` -- the pipeline writes status transitions, but humans may override (see Section 2)

## 2. Status Lifecycle State Machine

### States

| State | Set By | Meaning |
|-------|--------|---------|
| `submitted` | Human | Row is new. Human has filled in the URI and wants it processed. |
| `queued` | Pipeline | Pipeline has detected the row, assigned a `row_id`, and created a record in pipeline.db. |
| `fetching` | Pipeline | The fetch stage is downloading/reading the document content. |
| `parsing` | Pipeline | Content is being parsed (HTML to text, PDF extraction, etc.). |
| `extracting` | Pipeline | Entities and edges are being extracted via LLM. |
| `reviewing` | Pipeline | Extraction complete; entities/edges await human review approval. |
| `ingested` | Pipeline | Document fully processed and loaded into Neo4j + YAML. |
| `failed` | Pipeline | A pipeline stage failed. See `status_detail` for which stage and why. |
| `skipped` | Human/Pipeline | Document intentionally excluded from processing. |
| `duplicate` | Pipeline | URI already exists in pipeline.db with identical content hash. |
| `dead_letter` | Pipeline | Max retries exceeded. Requires manual intervention. |

### Valid Transitions

```
submitted -----> queued -----> fetching -----> parsing -----> extracting
                                                                |
                                                                v
                                                            reviewing -----> ingested
                                                                |
                                                                v
                                                            (human approves/rejects in KG CLI)

Any processing state -----> failed -----> submitted (human re-triggers)
                                     \--> dead_letter (max retries)

submitted -----> skipped (human decides not to process)
submitted -----> duplicate (pipeline detects existing URI)

ingested -----> submitted (human forces re-ingestion)
skipped  -----> submitted (human changes mind)
failed   -----> submitted (human retries)
```

### Human Override Rules

1. **Human sets status to `submitted`**: The pipeline treats this as a new submission
   regardless of prior state. If the document was previously ingested, the pipeline
   re-fetches and checks the content hash. If content is unchanged, it moves to
   `ingested` without re-extracting. If content changed, it re-processes fully and
   deprecates old entities.

2. **Human sets status to `skipped`**: The pipeline stops processing immediately
   (if in progress) and marks the pipeline.db record as skipped. No further polling.

3. **Human edits any other status value (e.g., types `queued` manually)**: The pipeline
   ignores unrecognized or out-of-sequence status values and logs a warning. It does
   not crash or re-process.

4. **Human deletes a row**: See Section 3 (Edge Cases).

## 3. Edge Case Decisions

### Row deleted by human after processing starts

**Decision**: The pipeline maintains its own state in pipeline.db. If a sheet row
disappears during or after processing, the pipeline:
- Detects the missing row on next poll (row_id no longer in sheet).
- Marks the pipeline.db record status as `orphaned`.
- Does NOT delete extracted entities/edges -- the knowledge is already in the graph
  and may be valid.
- Logs a warning: "Sheet row {row_id} was deleted; pipeline record {source_id} orphaned."
- If processing was in-flight, the current stage completes but no further stages run.

**Rationale**: Deleting a row is a UI action, not a knowledge retraction. If Alan wants
to retract knowledge, he should use the KG CLI review tools to reject entities.

### Status manually changed from "ingested" back to "submitted"

**Decision**: Treat as a re-ingestion request. The pipeline:
- Re-fetches the URI.
- Computes a new content hash.
- If content unchanged: fast-path back to `ingested` (no re-extraction).
- If content changed: full re-process, deprecate old entities via
  `db.deprecate_entities_for_source()`.

**Rationale**: This is the primary mechanism for updating stale documents. Content-hash
idempotency prevents unnecessary reprocessing.

### Duplicate URLs submitted

**Decision**: Flag as `duplicate` with a reference to the original row.
- On detection, set `status=duplicate` and `status_detail="Duplicate of row {original_row_id}"`.
- The human can override by changing status back to `submitted`, which forces
  a fresh fetch (useful if content has changed since the original ingestion).
- Deduplication is by normalized URI (lowercase, strip trailing slash, remove fragments).

### Partial failure (doc found but no entities extracted)

**Decision**: Surface clearly and do not mark as `ingested`.
- If fetch + parse succeed but extract yields zero entities:
  set `status=ingested` but `entity_count=0`, `edge_count=0`,
  `status_detail="No entities extracted -- document may not contain agentic technology content."`.
- This is a valid outcome (not all documents contain relevant entities).
- If extract itself fails (LLM error, malformed output): set `status=failed` with
  the error in `status_detail`.

### Sheet goes stale (no new rows, pipeline keeps polling)

**Decision**: Exponential backoff polling with an idle ceiling.
- Default poll interval: 60 seconds.
- After 5 consecutive polls with no new `submitted` rows: double the interval.
- Ceiling: 15 minutes between polls.
- Any new `submitted` row resets the interval to 60 seconds.
- The pipeline never stops polling entirely -- it just slows down.

### Who "owns" status updates

**Decision**: Shared ownership with last-write-wins semantics.
- The pipeline writes status as it progresses through stages.
- Humans can override status at any time.
- If human and pipeline write simultaneously, the pipeline's next poll picks up
  the human's value (sheet is the source of truth for status).
- The pipeline records its own status in pipeline.db independently, so sheet
  overrides do not corrupt internal state.

**Key principle**: The sheet is a communication interface, not the system of record.
pipeline.db is the system of record. The sheet reflects pipeline state and accepts
human intent signals.

## 4. Pipeline Integration

### Polling Architecture

```
Google Sheet (or CSV watcher)
       |
       | Poll every 60s (with backoff)
       v
Sheet Poller Service
       |
       | For each row where status = "submitted":
       |   1. Validate URI format
       |   2. Check for duplicates in pipeline.db
       |   3. Insert into pipeline.db sources table
       |   4. Update sheet: status -> "queued", set row_id, pipeline_source_id
       v
pipeline.db (sources table)
       |
       | Existing Prefect pipeline picks up pending sources
       v
Pipeline Stages: fetch -> parse -> chunk -> embed -> extract -> resolve -> review -> load
       |
       | After each stage, update sheet row status
       v
Sheet Status Writeback
       |
       | Update status, status_detail, entity_count, edge_count, last_updated
       v
Google Sheet (reflects current state)
```

### Mapping: Sheet Status to Pipeline Status

| Sheet Status | pipeline.db Status | pipeline.db Stage |
|-------------|-------------------|-------------------|
| `submitted` | (not yet in DB) | -- |
| `queued` | `pending` | -- |
| `fetching` | `processing` | `fetch` |
| `parsing` | `processing` | `parse` |
| `extracting` | `processing` | `extract` |
| `reviewing` | `pending_review` | `review` |
| `ingested` | `complete` | `load` |
| `failed` | `failed` | (last attempted) |
| `duplicate` | (not inserted) | -- |
| `dead_letter` | `dead_letter` | (last attempted) |
| `skipped` | (not inserted or marked skipped) | -- |

The sheet uses finer-grained statuses than pipeline.db because it serves as a
user-facing dashboard. The pipeline maps between the two representations.

### New Pipeline Component: Sheet Poller

A new module `src/agents_kg/sheet_poller.py` will:

1. Read the Google Sheet (via Sheets API) or watch a CSV file.
2. Scan for rows with `status=submitted`.
3. Validate and deduplicate.
4. Insert into pipeline.db via existing `db.add_source()`.
5. Write back `row_id`, `pipeline_source_id`, `status=queued`.
6. After each pipeline stage completes, update the sheet row's status.

This module is the only new code needed. The existing pipeline stages are unchanged.

### Submitter Email Integration

The `submitter` column maps directly to the existing `sources.submitter_email` field
in pipeline.db. This enables per-contributor tracking and future notification features.

## 5. Multi-Interface Support

### The `source_interface` Column

Every submission row carries a `source_interface` value indicating which input
mechanism created it. This enables:

- Tracking submission volume by interface.
- Interface-specific validation rules (e.g., CLI submissions skip sheet-specific fields).
- Future analytics on contributor behavior by channel.

### Supported Interfaces

| Interface | `source_interface` Value | How It Submits |
|-----------|------------------------|----------------|
| Google Sheet | `google_sheet` | Human fills in row; poller detects it |
| CLI | `cli` | `kg ingest <url>` command; writes directly to pipeline.db |
| REST API | `api` | Future HTTP endpoint for programmatic submission |
| Slack Bot | `slack_bot` | Future Slack integration for sharing links |

### Schema Compatibility

All interfaces write to the same pipeline.db sources table. The `source_interface`
value is stored as metadata. The sheet is just one view into the ingestion queue.

For CLI-originated submissions that should appear in the sheet (for Alan's visibility),
the sheet poller can optionally sync pipeline.db records back into the sheet with
`source_interface=cli`.

## 6. Data Validation Rules

The sheet poller validates each row before queuing:

| Field | Validation | On Failure |
|-------|-----------|------------|
| `uri` | Must be a valid URL (http/https), file path, or `inline:*` | Set `status=failed`, `status_detail="Invalid URI format"` |
| `source_type` | Must be one of: `authoritative`, `theoretical`, `speculative` | Default to `theoretical` with warning in `status_detail` |
| `submitter` | Must not be blank | Set `status=failed`, `status_detail="Submitter required"` |
| `content_snippet` | If `uri` starts with `inline:`, snippet must not be blank | Set `status=failed`, `status_detail="Inline URI requires content_snippet"` |

## 7. Sheet Formatting Recommendations

For the Google Sheet implementation:

- **Header row**: Frozen, bold, with background color per ownership category
  (blue = human-writable, green = pipeline-writable, yellow = shared).
- **Status column**: Data validation dropdown restricted to valid status values.
- **Conditional formatting**: Color-code status cells
  (green = ingested, red = failed/dead_letter, yellow = processing states, gray = skipped/duplicate).
- **Protected ranges**: Pipeline-writable columns should be protected with a warning
  (not locked -- humans may need to fix data, but should know the pipeline will overwrite).
- **Notes column**: Unformatted, wide, for free-text annotations.
